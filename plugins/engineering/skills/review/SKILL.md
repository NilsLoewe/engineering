# review

You orchestrate; you do not review. Reviewers are subagents that did not write the code (rule 5). `$T` = `python3 ${CLAUDE_PLUGIN_ROOT}/tools/tracker.py` (add `--config <file>` when a world overlay in your context names an engineering tracker config).

1. **Gather.** `gh pr view <n> -R <repo> --json title,body,headRefOid,files` and `gh pr diff <n> -R <repo>`. Ticket link in the body → `$T read <ref>`, take the `🤖 clarify · spec` comment. No spec → say so in the review body; review against the PR text.
2. **Pick lenses.** Read `${CLAUDE_PLUGIN_ROOT}/generated/linsen/index.json` and every lens index a world overlay in your context names. A lens applies when a changed file matches its `pfade` and, if it has `inhalt`, an added line matches that regex. At most 4 lenses; prefer the ones whose files the diff touches most.
3. **Review in parallel.** One general-purpose subagent per lens plus one general reviewer, each with: the diff, the spec, its lens file (the general reviewer: core and world rules from context, plus "does the code do what the spec says, and nothing else", plus the three checks humans still caught after agent review: **the other side** - for every field, parameter or signal crossing a repo, open the other repo's source at its default branch (`git -C <clone> show origin/HEAD:<path>`) and compare type, null vs empty, ranges, version; **bypass paths** - for every new validation, scope or guard, grep for writers that skip it (bulk update, raw SQL, imports, unscoped reads); **every id from the request** checked against the acting tenant and user). Task: "Report only real problems you can point to in the diff, as JSON `[{path, line, severity, rule, text}]`; line = line number in the new file; severity blocker (breaks data, security, the spec) | major (wrong behaviour a user would hit, even if rare; missing test for a new branch) | minor (maintainability only); text = what is wrong, why it matters, the fix, ≤ 4 sentences. No style taste, no praise, no summary."
4. **Merge.** One list; drop duplicates (same path, nearby line, same problem); keep at most 5 minor. A finding without a concrete line goes in with the nearest changed line or none. Then write the **brief** for the human reviewer: `check` = up to 5 points only a person can judge here (product rules nobody confirmed in the spec, domain behaviour, contracts no reviewer could read, tenancy, deploy order), each with a pointer; `skip` = up to 5 things a reviewer verified with evidence (file:line). No generic advice.
5. **Post.** Write `{"findings": [...], "brief": {"check": [...], "skip": [...]}}` to a file of its own (`review-<repo>-<pr>.json` in your scratchpad, never a shared name), then `python3 ${CLAUDE_PLUGIN_ROOT}/tools/review_post.py <repo> <n> <file>` (add `--dry-run` for a dry run). It posts one review with event COMMENT; lines GitHub cannot anchor go into the body.
6. **Report** in 3 lines: counts by severity, the most serious finding, the review link. Whether blocker/major block the merge is the world's rule (see its context). If the PR already has three or more agent reviews and none of the last three had a blocker or major, say "hand over to a human" instead of suggesting another round: more rounds only find new minors.

Repeated findings of the same kind across PRs are rule candidates for the world catalog (rule 6); name them, do not add them yourself.
